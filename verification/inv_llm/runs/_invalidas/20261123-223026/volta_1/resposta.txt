```c
static int inv_extra(const argus_ctx_t *c)
{
    int i, j;
    const int N = 0x3FFFFFFF;
    for (i = 0; i < ARGUS_MAX_TRACKS; i++) {
        int k;
        if (c->tracks[i].active != 0 && c->tracks[i].active != 1) return 0;
        if (!c->tracks[i].active) continue;
        if (c->tracks[i].id < 1 || c->tracks[i].id > N) return 0;
        /* ids emitidos desde a criacao deste track (ciclico em [1,N]) */
        k = c->next_id - c->tracks[i].id;
        if (k <= 0) k += N;
        if (k < 1 || k > c->tracks[i].age * MAX_DETS) return 0;
        for (j = i + 1; j < ARGUS_MAX_TRACKS; j++)
            if (c->tracks[j].active == 1 && c->tracks[j].id == c->tracks[i].id)
                return 0;
    }
    return 1;
}
```

**Por que o estado do contraexemplo é inalcançável.** No estado de partida, um track tem `active = -2147483648`, valor que nunca ocorre: `argus_init` e `argus_update` só escrevem 0 ou 1. O outro track tem `id = 1073741823`, igual a `next_id`. Ao reusar o slot, o novo track recebe o mesmo `id`, e o harness deixa de ver a finalização, o que quebra P4. Numa execução real, um track ativo nunca tem `id == next_id`.

**Por que se preserva em um frame.**
1. Um track recém-criado recebe `id = next_id` com `age = 1`, e `next_id` avança, então `k = 1 ≤ age*MAX_DETS`. A cada frame, `age` sobe 1 e no máximo MAX_DETS ids novos são emitidos, logo `k` cresce no máximo MAX_DETS.
2. Como `age ≤ ARGUS_MAX_AGE = 60`, `k` fica muito abaixo do período 2^30 do wrap. Assim `k ≥ 1` se mantém, e nenhum track ativo pode ter `id == next_id`.
3. Por isso cada novo id difere de todos os ids ativos, e a unicidade se mantém; `active` continua em {0,1} porque o código só escreve esses valores.
